## Update — 2026-11-15 (detection evaluation: precision, recall, F1 and false positive rate)

The previous status listed "measure the false alarm rate" as open. A framework now exists in `research/` (see `research/README.md`) and two reports were produced from it. Both are partial answers and are labelled as such.

- **What was built.** A seeded simulator of labelled networks (11 benign profiles, 16 attack families; hard cases on both sides: a mistyped password, a NAT gateway, a scheduled scanner, Office and WMI automation, installers in Temp, approved cloud changes, and slow attacks built to stay under thresholds), four methods compared on the same held-out entities, metrics with 95 % Wilson intervals, a threshold sweep per rule, and a precision-versus-prevalence projection. The rule evaluators used are the ingestion pipeline's own (`app/detection/evaluate.py`, shared with `run.py`).
- **Simulation result** (20 seeds, 500 entities, 10 % attackers, 14 % of benign entities behave suspiciously; `research/results/RAPOR.md`): rules precision 37.5 %, recall 78.4 %, F1 50.7 %, false positive rate 13.4 %; plain threshold baseline precision 63.2 %, recall 46.4 %, F1 53.5 %, FPR 2.8 %; Isolation Forest precision 35.0 %, recall 17.3 %, F1 23.1 %, FPR 3.3 %. When 39 % of benign entities behave suspiciously the rules' FPR is 38 % and F1 28.5 %. The rules catch fast attacks and endpoint, cloud and persistence events the baseline cannot see, miss every slow attack (the fixed windows and thresholds), and fire on legitimate automation, NAT gateways, scanners and forgetful users. The Isolation Forest adds little over the rules. At realistic attacker shares (1 % or less) the projected precision of every method is low.
- **These numbers describe the simulator's assumptions, not a real network.** The generator and the rules were written by the same people, which favours the rules, and nothing was tuned on the data; the baseline also sees whole-period totals per entity, which a streaming rule cannot.
- **Real attack captures** (`research/results/GERCEK_VERI.md`): eight public Windows captures from OTRF Security-Datasets (4.5 MB, SHA-256 checked, read as data only). The expected rule for each was fixed from the documented technique before running. Five of eight fired the expected rule (scheduled task, account creation, audit policy change, script host starting PowerShell, mshta starting PowerShell). The three misses had different causes found by looking at the captures afterwards: a service install logged only as System event 7045 (the sensor reads the Security log only), a WMI-spawned PowerShell visible only in Sysmon, and an implant started by WmiPrvSE that the WMI rules do not match because they only accept powershell.exe and cmd.exe as the child. No rule was changed because of this; a broader WMI rule would be tuned on one capture. There is no benign counterpart, so no false positive rate comes from real data.
- **Not done:** an evaluation on a public labelled data set that contains both benign and attack traffic (CICIDS2017, UNSW-NB15 or similar; the loader and runner accept a converted file), a supervised model, any tuning of thresholds on a separate validation set, and a comparison against an external detection engine.
- **Side change:** the login-pattern rule's minimum number of failures (3) is now a rule parameter (`min_failures`) so the sweep can vary it. Behaviour is unchanged.

## Update — 2026-11-15 (sessions, passwords and readability; a separate branch, not yet on the live stack)

- **Why a session lasted 10 days.** Every refresh issued a brand-new refresh token with a full 8-hour life and nothing carried the time of the original sign-in forward, so a session that was used (or merely polled: the interface asks for pending approvals every 20 seconds and silently refreshes on any 401) never expired. The 8 hours were a sliding idle window, not a limit. No server setting was wrong (`REFRESH_TOKEN_HOURS` was 8).
- **Fixed (backend, with tests written first).** The refresh token now carries the sign-in time (`sat`); rotation keeps it, the new token expires at the earlier of 8 hours or `SESSION_MAX_HOURS` (default 12) after the sign-in, and a refresh past that returns `session_expired`. Tokens issued before this change have no `sat`; they are treated as signed in at their own issue time, so an old session survives at most one more rotation window and is then capped.

The policy (12 to 128 characters, at least six distinct characters, letters mixed with digits, symbols or case, not a common word, not containing the account name, not equal to the current password) also applies to new accounts. Wrong attempts are audited (`auth.password_change_failed`); `confirm_password` is never written to the audit log.

The Users page asks for the administrator's own password before a reset and no longer offers a reset on one's own row. ## Update — 2026-11-15 (continuous improvement: sensor watchdog, token reuse, audit copies, links, contrast)

- **Sensor restarts itself.** The local controller now restarts a sensor process that died on its own, with the same settings, waiting 10 seconds and doubling (at least a minute after a crash within 20 seconds), at most 5 times an hour; a stop asked for by a person or an access revoked on the server is never restarted. The Sensors page says when a restart is pending or given up. Eight unit tests with a fake clock; **not tried against a real crashing sensor on Windows**.
- **Stolen refresh token detection (migration 020).** A refresh token that was replaced and is presented again more than 15 seconds later ends the whole session (`token_reuse`, audited `auth.refresh_reuse_detected`); within 15 seconds it is only refused, so two browser tabs racing for a renewal do not log the person out.
- **Audit log copies (migration 021).** Administrators can add HTTPS destinations (a SIEM or archive). Every minute new rows go out in batches with the hash of the last row; a failing destination is retried with a growing wait and the position only moves after a batch is accepted; the address is stored encrypted and never returned. This closes the gap noted before (newest rows removed without trace). Shown on the Audit page.
